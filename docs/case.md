# AI 发布门禁平台 · 案例（一页版）

> 一句话：让「改了一版 prompt / 换了一次模型」这件事，从"上线后看用户反馈"变成
> **上线前自动跑评测、不达标自动回滚、全过程可审计**。

## 1. 要解决的问题

问答类应用的迭代很轻：改几句话术、换一版模型、调一下检索参数，就是一次发布。
但发布之后有三件事答不出来：

1. **有没有变差？**（没有上线前的量化对比，只能等用户抱怨）
2. **最近改了什么？**（配置散在代码和 .env 里，没有版本号）
3. **出事怎么退？**（要么手工改回去，要么重新发一版旧代码）

## 2. 为什么是这套方案

| 备选 | 为什么不够 |
|---|---|
| 靠人 review | 能看"改得对不对"，看不出"效果有没有变差" |
| 只看线上监控 | 发现时用户已经受影响；且异常 ≠ 质量下降（也可能只是流量变了） |
| 每次全量重跑评测 | 一次几分钟到几十分钟，挡不住日常小改动 |

选了"**灰度 + 子集评测门禁 + 一键回滚**"：评测只跑 20 题回归子集（分钟级），
通过就放量，不通过自动回滚，全量评测留给离线。

## 3. 怎么搭的

```text
            ┌─────────────┐  建发布（校验版本存在，fail-closed）
            │ config-svc  │◀──────────────┐
            │  8081       │               │
            └─────────────┘        ┌──────┴───────┐
                                   │ release-svc  │  灰度 / 放量 / 回滚 / 审计
                                   │   8082       │  状态机 + rev 乐观锁
                                   └──────┬───────┘
                          同事务写 outbox │
                                          ▼
                              Redis Streams（至少一次）
                                          │
                                   ┌──────┴───────┐
                                   │  gate-svc    │  消费去重（uk_event）/ 重投
                                   │   8083       │
                                   └──────┬───────┘
                             提交（202，不等）│ 回调（score + passed）
                                          ▼
                                ┌──────────────────┐
                                │ eval-executor    │  Python，打被评测服务
                                │   8084           │  20 题均匀抽样、命中率
                                └──────────────────┘
```

四个服务、三个独立库（`arg_config` / `arg_release` / `arg_gate`）——
按"读多写少 / 事务写 / 长任务"分，故障域不同。

## 4. 四个关键决策（每条都写清"为什么不选另一个"）

| 决策 | 为什么 |
|---|---|
| **outbox 表 + 扫表投递**，不是"写完直接 XADD" | 直接发有两个窗口：事务回滚但消息已发（幽灵事件）、事务提交但进程崩了（丢事件）。outbox 把"写业务"和"记事件"合成一个事务，投递失败下轮重试 ⇒ 至少一次；重复由消费端唯一索引去掉 |
| **回滚 = 改指针**，不是重新发布旧版本 | 重新发布要重新走一遍校验与门禁，慢且可能失败；指针切换是 O(1)、幂等，且"回滚"和"发布"不会互相打脸 |
| **门禁阈值由发布方声明**，不是全局写死 | 改一版 prompt 的风险和换模型不一样大；写死等于所有发布共用一个标准，出了事说不清"为什么这次放行" |
| **提交 + 回调**，不是同步等评测 | 一次评测 20~80 秒。同步等会占满线程、触发超时重试；拆开之后两侧都能独立重试 |

## 5. 怎么证明它是对的

11 条判据，每条都有"坏情况下会不会响"的反向验证（`scripts/smoke_*.py`）：

| 判据 | 数字 |
|---|---|
| 幂等建版本 + 原子发号 | 30 并发 → 30 个版本、1..30 无重号 |
| 灰度稳定性 | 同租户 1000 次结论一致；桶号与 Python 独立实现 20/20 一致 |
| 并发安全 | 过期 `rev` 改状态 → 409（不是 500、不是静默成功） |
| 消息幂等 | 同一事件投 **100** 次 → 只建 **1** 个任务；消费后 pending = 0 |
| 门禁闭环 | 真评测 18/20 = 0.90；门槛 0.80 通过、0.95 自动回滚 |
| 回调幂等 | 同一 job 回调 3 次 → `changed=false` × 3，发布不被二次回滚 |
| 可观测 | traceId 跨 4 个进程可串（含异步消息那段） |
| 容量 | `/api/gray` 约 2000 rps 饱和，16 并发内 p95 < 16ms |
| 故障 | 执行器宕机：发布照常成功、任务不丢、恢复后自愈 |

## 6. 三个真踩到的坑

1. **旧进程假绿**（同类事故第 3 次）：8084 上还是旧执行器，新进程 bind 失败退出，
   判据"通过"其实跑的是 stub。修法不是"下次小心"，而是让 `/ping` 报 `evalKind` 与代码 mtime，
   判据第一步就断言"我跟预期的那份代码在说话"。
2. **429 被当成答错**：同一版本跑出 0.90 和 0.70，快的那次是请求被限流。
   修法：429/5xx 重试退避、失败记 `errored` 不记 0、错误率 > 10% 拒绝判决（宁可不判，不拿脏数据判决）。
3. **长任务打穿扫描器假设**：真评测 20~80 秒，而扫描器"RUNNING 5 秒没动就重投"⇒
   正常任务被当成卡死。修法：提交失败放回 QUEUED（快速重投），RUNNING 用 300 秒租约。

## 7. 已知边界（不藏）

- **评测对象是"线上现状"，不是"候选版本"**：候选版本的配置在 config-svc 里，
  被评测服务还没接"按版本取配置"。要做到真评候选版本，需要被评测服务接入 config-svc。
- **没有单元测试**：目前靠 8 个端到端判据脚本 + 手工核对；单元测试是下一步。
- **重试无退避**：提交失败每 5 秒重投，5 次用光只需 25 秒；应改成指数退避。
- 单机部署，未做多实例下的一致性验证（乐观锁与唯一索引本身与实例数无关，但没量过）。

## 8. 规模
